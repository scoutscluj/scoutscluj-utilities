# Design: Optimize Inventory Image Loading

## Context

The inventory web route requests up to 100 items by default. For every item with an image, the desktop table renders an image in a 46 by 46 pixel container and the mobile card markup renders the same protected URL in an 84 by 84 pixel container. Both contexts currently point at the original-image endpoint without native lazy loading or asynchronous decoding.

The original files visible in the reported browser trace are commonly 1.5 MB to 6.8 MB. The 30 visible requests in that trace represent approximately 88 MB even though the images are presented as small previews.

The API has a second amplification point. `InventoryService.getImagesForItems` loads complete `InventoryItemImage` entities to serialize metadata for the list response. Because `fileData` is a normal scalar `bytea` property, list serialization reads the image bytes even though it omits them from JSON. Each browser request then loads the original bytes again. The SvelteKit proxy buffers the upstream response with `arrayBuffer()` before returning it.

The existing inventory design requires authenticated image access and intentionally stores image bytes in PostgreSQL. This change retains both decisions.

## Goals

- Make initial inventory rendering independent of original-image file sizes.
- Ensure inventory list queries never hydrate image binary columns.
- Keep table and mobile previews small enough for constrained mobile networks.
- Preserve explicit authenticated access to the original image.
- Preserve safe replacement semantics when an upload is corrupt or cannot be transformed.
- Provide a bounded, observable migration path for existing images.
- Prevent regressions with deterministic API and browser acceptance checks.

## Non-Goals

- Introduce object storage, public URLs, CDN signing, or a generic image service.
- Modify or discard original image bytes.
- Optimize every in-memory inventory filtering and sorting operation.
- Guarantee that an intentionally opened multi-megabyte original loads instantly.

## Decisions

### Persist One Thumbnail Per Image

Add the following nullable columns to `inventory_item_images`:

- `thumbnail_content_type`;
- `thumbnail_file_size`;
- `thumbnail_checksum_sha256`;
- `thumbnail_data` as `bytea`.

The thumbnail is derived deterministically from the original using `sharp`:

- decode and validate the actual image bytes;
- apply embedded orientation with `rotate()`;
- resize to 192 by 192 pixels with `fit: cover` and without enlargement;
- encode WebP at a fixed quality near 75;
- hash the generated bytes with SHA-256.

One 192-pixel derivative is sufficient for the existing 46-pixel desktop and 84-pixel mobile previews, including common high-density displays, while keeping the model and backfill simple. A typical target is 10 KB to 40 KB per thumbnail; tests should assert dimensions and encoding rather than a universal hard byte limit because image complexity varies.

Thumbnail generation happens before the existing image row is mutated. If decoding or transformation fails, the API rejects the upload and leaves the previous original and thumbnail unchanged. Original and thumbnail metadata are persisted in the same flush/transaction boundary.

### Keep Binary Columns Out Of List Queries

Inventory list serialization will fetch an explicit metadata projection for image-bearing items. Neither `file_data` nor `thumbnail_data` may be part of that projection. The list response continues to expose protected image metadata, with enough thumbnail metadata to construct a versioned protected URL.

The original and thumbnail delivery paths use dedicated queries that select the requested binary payload. Tests must cover the projection so a future entity change cannot silently reintroduce blob hydration.

### Use Separate Protected Delivery Paths

Keep the existing endpoint for explicit original viewing:

- `GET /api/inventory/items/:id/image`

Add a dedicated preview endpoint:

- `GET /api/inventory/items/:id/image/thumbnail`

Add the corresponding authenticated SvelteKit proxy route. Table and card `<img>` elements use only the thumbnail route. The surrounding link continues to target the original route.

Both endpoints remain behind the existing authenticated inventory read policy. Missing or failed legacy thumbnails return not found and the UI shows its existing image placeholder; the browser must not silently fall back to downloading the original as a preview.

### Version And Conditionally Cache Image Responses

Thumbnail metadata includes its checksum, and the web app appends that value as a version query parameter. Replacing an image therefore changes the preview URL immediately.

The API returns a strong ETag derived from the bytes' checksum and honors `If-None-Match` with `304 Not Modified`. The SvelteKit proxy forwards validators and relevant response headers. Responses use private browser caching, retaining the current short freshness window while allowing stale entries to revalidate without retransmitting unchanged bytes.

The proxy returns the upstream body stream instead of first materializing an `ArrayBuffer`. It forwards at least content type, content length, content disposition, ETag, and cache control. Authentication still occurs for requests that reach the proxy; no shared or public cache is introduced.

### Load Preview Images Defensively

Desktop and mobile preview elements use:

- `loading="lazy"`;
- `decoding="async"`;
- low fetch priority;
- explicit width and height matching their layout containers.

This makes off-screen work deferrable, avoids layout movement, and ensures the browser decodes the small derivative rather than a full-resolution source. Column visibility and responsive markup may remain client-managed, but neither hidden nor visible preview markup may reference the original endpoint.

## Existing Data And Import

Add a production-capable backfill command that:

- selects only records with missing thumbnail fields;
- processes records in bounded primary-key batches;
- limits concurrent `sharp` work;
- commits progress incrementally;
- is idempotent and resumable;
- reports processed, skipped, and failed image IDs without logging image bytes;
- exits non-zero when failures remain.

The legacy inventory importer will generate the same thumbnail bytes and metadata for future imports. Offline generated SQL includes both the original and thumbnail values.

Invalid existing originals are not deleted or rewritten. They remain accessible through the original endpoint if the browser supports them, while their preview uses a placeholder until an operator resolves the data issue.

## Rollout

1. Add nullable thumbnail columns and deploy metadata-only list queries, upload-time thumbnail generation, delivery endpoints, and backfill tooling.
2. Verify new uploads produce a valid original and thumbnail atomically.
3. Run the resumable backfill in bounded batches and review failures.
4. Switch table and mobile preview markup to versioned thumbnail URLs with lazy loading.
5. Verify production-like network and memory behavior before completing the inventory smoke-test acceptance.

The metadata-only projection can be released before the UI switch and provides immediate API memory relief. The UI should not switch existing records until the backfill has completed or the placeholder behavior has been explicitly accepted.

## Acceptance And Observability

- Inventory list SQL does not select `file_data` or `thumbnail_data`.
- Initial desktop and mobile inventory rendering makes no request to the original-image endpoint.
- Off-screen thumbnails are eligible for native lazy loading.
- The reported 30-image case transfers thumbnail-scale data rather than approximately 88 MB of originals.
- Revalidating an unchanged image can return `304 Not Modified`.
- Replacing an image produces a different versioned thumbnail URL.
- The API and SvelteKit process do not buffer all page originals during inventory rendering.
- Logs and backfill output contain identifiers and metadata, never binary content or session credentials.

## Risks And Mitigations

- **Backfill CPU and database load:** use bounded batches, limited concurrency, incremental commits, and an operator-selected execution window.
- **Corrupt or unsupported imported images:** isolate failures, preserve originals, show placeholders, and produce a retryable report.
- **HEIC support differences between `sharp` builds:** exercise the production container build during validation and fail safely without replacing existing records.
- **Stale authenticated browser content:** keep cache scope private, use a short freshness lifetime, version URLs on replacement, and revalidate stale entries through the authenticated proxy.
- **Schema growth:** thumbnail storage is expected to be tens of kilobytes per image and remains small relative to the retained originals.

## Alternatives Considered

### Frontend Lazy Loading Only

Rejected as the complete solution. It reduces off-screen requests but still sends multi-megabyte originals for visible rows and does not prevent API list queries from hydrating image bytes.

### Generate Thumbnails On First Request

Rejected because the first viewer would pay the decode/resize cost and a page containing many uncached images could create a concurrent CPU spike. Persisted generation at upload/backfill time makes request cost predictable.

### Reduce Page Size

Rejected as the primary remedy because it only lowers the multiplier and changes the operational scanning experience. It can be evaluated independently if non-image DOM size becomes a measured problem.

### Object Storage And CDN

Deferred. It adds infrastructure and protected-delivery complexity without addressing the incorrect use of originals as thumbnails. The endpoint contract allows storage to move later if PostgreSQL becomes unsuitable.

## Rollback

The web app can revert preview URLs to the prior protected original endpoint while the nullable thumbnail columns remain in place. The thumbnail endpoint and backfill command can be disabled without deleting generated data. Production rollback must not drop original or thumbnail bytes unless a separate data-retention decision authorizes it.
