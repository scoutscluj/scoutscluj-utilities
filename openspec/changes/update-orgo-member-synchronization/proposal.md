# Refresh Orgo members on opening the roster and synchronize shared edits

## Why

A member reactivated in Orgo can remain missing from Resurse. The current
refresh visits only existing linked records, does not reconcile lifecycle
status, and is gated by a daily check. The dashboard also separates imported
inactive members from the main table. Outgoing operations already use an
outbox, but transient errors and stale revisions often require manual action.

## What Changes

- Opening the member workspace shows cached authorized rows immediately and
  starts a server-side Orgo refresh. The table updates when it completes and
  displays progress, last successful refresh, failure and retry.
- Refresh discovers members by canonical Orgo ID across the complete configured
  center roster, including active, inactive and suspended records. Existing
  identities and links are reused; ambiguous matches require review.
- All statuses appear in one main member table, with common search, filters,
  sorting, pagination and selection. Remove the separate inactive-history table.
- Shared-field edits, including withdrawal/reactivation, are saved locally with
  an outbox operation in the same transaction. Attempt delivery promptly after
  commit, retry temporary failures automatically, and verify remote writes.
- For competing edits to the same shared field, the current Orgo value wins
  automatically. A local-only pending change remains pending when Orgo has not
  changed that field. Record superseded edits in audit without blocking unrelated
  fields or retaining a manual local-wins action.
- Resurse owns local structure, category, unit/subunit placement and local
  responsibilities. Refresh does not replace these with Orgo structure data,
  and local organization edits do not create misleading failed Orgo operations.
- Preserve distinct suspended, inactive and withdrawn representations/provenance;
  do not label every inactive person as withdrawn. Unknown statuses need review.
- Withdrawal is center-wide, ends involvement and authority, and preserves
  history. Reactivation restores visibility without restoring ended mandates or
  administrator privileges. Status changes in Resurse must be sent to Orgo.

## Impact and compatibility

API member reconciliation, outbox/worker, lifecycle services, persistence,
member workspace/table and scoped serializers. Reuse member IDs, account links,
existing source aliases, history and financial records. Keep financial writes
under the existing lock order and lifecycle eligibility rules; historical
payments/obligations are never regenerated by a refresh.

This proposal supersedes incompatible rules in `add-unit-member-management`,
`extend-orgo-member-profiles` and `refactor-member-organization`: daily-only
freshness, separate inactive history, manual conflict choice, permanent local
status overrides, and remote projection over established local organization.
It does not redesign activity/event synchronization or financial settlement.
Implementation must inventory member mutation paths so equivalent edits from
the table, member file, bulk actions and self-service share the same contract.

## Integration evidence and remaining limits

Repository evidence records successful server-token reads of `/api/v1/users`,
`/api/v1/users/{id}` and `/api/v1/units`. The adapter implements profile PATCH,
contact and configured status writes, plus photo upload with readback.
Implementation of a request is not proof that the tenant permits it.

`docs/product/unit-member-management.md` records an empty PATCH rejected with
HTTP 403 on 2026-10-20. This session has not reverified live token permissions.
Automatic remote delivery requires an authorized edit-capable token and verified
status mapping. `ACTIVE`, `INACTIVE`, `SUSPENDED` were observed, but the recorded
evidence does not confirm that `INACTIVE` is the correct withdrawal write value.
Do not guess that mapping or enable writes based only on adapter support.

Inbound refresh, the unified table and honest pending states can be implemented
while those external prerequisites are resolved. Unsupported operations and
permission failures remain visible and are never reported as remote success.
